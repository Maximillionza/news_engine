# ACE v4.0.2 — Build Notes

## What this delivery is

ACE v4.0.2 is a fork of v4.0.1 (including Addendum 14, the 6-pair DXY basket) into its own source tree, `ACE_v4.0.2\`. It no longer shares include files with the older builds. v4.0.0 must not be recompiled from the old shared tree: the control builds compile from `Claude_ACE_v4.0.0_rebaselined\`, which this delivery does not touch. The legacy execution cascade is unchanged. Every change below is in the V4 learning layer and in trade attribution/export.

State files start fresh. The version tag `ASE_v4.0.2` gives new `adaptive2` and `v4state2` file names, so nothing is inherited from v4.0.1. The earlier counts were contaminated by the bugs below: wrong liquidity attribution, double counting, raw money counted as R, and no out-of-sample (OOS) data. Carrying them over would have been wrong anyway.

## Phase 0 — learning-integrity fixes

**1. Canonical setup DNA.** `ASE_BuildSetupDNA` (Models/ASE_ConfluenceTypes.mqh) used to emit tags in the order the evidence was stored, so the same evidence set could produce different DNA strings. That split one setup across several DNA buckets and caused false "new occurrence" edges in the dedup. Tags are now emitted in ascending evidence-type order. The tag set, the exclusions and the output format are unchanged.

**2. Stable opportunity ID and entry snapshot.** `RecordOpportunity` returns "" while a DNA persists, and the StateMachine overwrote `m_v4LastOpportunityId` with it on every tick, so a closed trade was almost never linked to its opportunity. The StateMachine now keeps the last non-empty ID. On a successful Execute it snapshots the confluence result, opportunity ID, regime and liquidity-sweep flag (`m_v4Entry*`). `RecordClosedTrade` attributes from this snapshot, including `rec.v4OpportunityId` and the v4 archetype/grade/score columns. It no longer reads the live fields, which later ticks had overwritten. `ConfluenceResult` gains `hasLiquiditySweep`. `CASE_AdaptiveEngine::RecordOutcome` now takes the liquidity flag per outcome instead of `m_lastHasLiquidity`, which held whatever setup had been observed last.

**3. No double counting.** When the legacy cascade traded a setup, its theoretical twin also resolved and was fed to the adaptive engine, on top of the real trade close. The same setup was counted twice. `MarkLegacyTraded(dna)` now flags the pending theoretical on Execute. Flagged outcomes are skipped in the resolution loop, and Phase 1 will route them to a comparison ledger. Pending rows now persist under a new `PENDING2` tag (adds hasLiq, oppId, legacyTraded). Old `PENDING` rows still load with default values.

**4. Realised R guard.** When money-at-risk was 0, the adaptive engine was fed the raw money profit as if it were R, which is a unit error and can be a very large value. When risk is unknown the outcome is now not recorded, and a one-line warning with the ticket is printed. A realised R is computed for every closed trade, stored in `m_lastClosedRealisedR` and `TradeRecord.realisedR`, and exported as a new last column `realised_r` in the CSV, pipe and JSON attribution files. Legacy trades that V4 classified ARCH_NONE still do not reach `RecordOutcome`, and Phase 1 will handle them.

**5. Periodic save.** V4 learning state was saved only on deinit, so a crash, a VPS kill or a terminal stop lost everything learned since attach. Both engines now save once per new M15 bar, at the top of `Update()`, in every state. This runs only when `InpAceV4Mode >= ACEV4_EVIDENCE`. `CASE_SetupAnalytics::SaveState` is now public.

**6. OOS holdout.** With the default empty `InpAceV4OOSStartDate`, `IsOOS` always returned false. `oosSamples` could never grow, so `validated` could never become true. There are two new inputs: `InpAceV4OOSMode` (default 1 = interleaved) and `InpAceV4OOSEveryK` (default 5, so 20% of outcomes are held out). In mode 1, an outcome is OOS when a deterministic hash of its opportunity ID, mod K, is 0. Mode 0 keeps the old date split. OOS outcomes now update only the OOS fields. They no longer feed sumR/wins/recent/halves/cumulative/drawdown or the liquidity split, and those are the inputs to adaptation. The same separation applies to the shadow arms. Behaviour change: in-sample averages now exclude the held-out 20%.

**7. Reason strings.** The adaptive decision reason said "TrendContinuation" whatever the archetype was. It now uses the real archetype name.

## Amendment — provenance-stamped state migration

**Why this exists.** State files start fresh at every version tag by design (see above: `ASE_v4.0.2` gets its own `adaptive2`/`v4state2` filenames, nothing is inherited from `ASE_v4.0.1`). That reset was correct for the v4.0.1 → v4.0.2 jump specifically, because v4.0.1's counters were proven corrupted by the six integrity bugs above (wrong liquidity attribution, double counting, raw money counted as R, no OOS data, DNA dedup splitting one setup into several buckets, and the reason-string bug). It is not correct as a permanent policy — learning shouldn't reset on every version bump once a build's data is trustworthy. Losing 100+ observations' worth of accumulated authority tier every time a `.mq5` gets a new version number defeats the entire point of a graduated learning clock. This amendment gives future version bumps a way to carry forward a prior version's learning state, but only when that state can be proven trustworthy first.

**How the CLEAN stamp makes provenance structural, not a judgement call.** `CASE_AdaptiveEngine::SaveState()` and `CASE_SetupAnalytics::SaveState()` each now write a `CLEAN,1,<ASE_VERSION_TAG>,<utcTimestamp>` row on every save. A state file produced by this integrity-fixed build (or any later one) carries that row; a state file produced by a pre-fix build — v4.0.1 and earlier — does not, because those builds' `SaveState()` never wrote it. `IsClean(string &versionTagOut)` on both classes reports whether the file just loaded had that row, and which version stamped it. `CASE_LearningMigrator` refuses migration outright if either source file is not clean, with the reason "source not stamped clean (produced by a pre-integrity-fix build)". This means provenance is checked from the file's own contents, not from a human remembering which builds were trustworthy.

**What the validation pass checks.** Before any merge, `CASE_LearningMigrator::Migrate()` runs a full pass across all 5 archetypes on the source's LIVE and both SHADOW arms: `wins <= samples`, `oosWins <= oosSamples`, `oosSamples <= samples`, that `sumR`/`oosSumR`/`maxDrawdownR`/`cumulativeR`/`peakR` are not NaN and not absurdly large (`MathAbs(x) < 1,000,000`), that `sum(regimeSamples[0..4]) <= samples`, and that `threshold` sits inside `[70,90]` — the actual range `CASE_AdaptiveEngine::Observe()`'s own nudge logic ever moves it through (`threshold>70.0` to decrease, `threshold<90.0` to increase, starting from a default of 80.0). Every failure across every archetype is collected into one report string before refusing — the log says everything wrong at once, not just the first problem found.

**Merge is additive, not overwrite.** If validation passes, `CASE_AdaptiveEngine::MergeLiveState()`/`MergeShadowState()` and `CASE_SetupAnalytics::MergeLearningTables()` ADD the source's samples/wins/sumR/oosSamples/oosWins/oosSumR/regimeSamples/cumulativeR into the current (already-initialized, still-fresh) instance's own counters, take the max of the two `maxDrawdownR` values, and import `threshold` directly (it is a tuned parameter, not a count, and the current instance is fresh so there is nothing to add it to). `validated` is recomputed afterward using the exact same six-condition expression `RecordOutcome()` uses, pulled into a shared `RecomputeValidated()` helper so the two paths cannot drift apart. `SetupAnalytics`' five learning tables (GLOBAL/ARCH/ARCHDIR/REGIME/DNA) merge matching keys additively and insert source-only keys (e.g. DNA strings the current run hasn't seen yet) fresh via the existing `GetOrCreate()` path.

**Off by default.** `InpAceV4MigrateFromTag` (Models/ASE_Config.mqh) is empty by default and must be set deliberately to the exact prior `ASE_VERSION_TAG` string to import from. It is empty for v4.0.2 itself — nothing clean exists yet to import from, since this is the build that introduces the CLEAN stamp in the first place. This machinery is scaffolding proved out for real at the NEXT version bump: ship v4.0.3, run it once with `InpAceV4MigrateFromTag="ASE_v4.0.2"`, and confirm the `MIGRATION` audit row and the merged counters look right before relying on it.

Migration is also gated on the run being genuinely fresh: `CASE_StateMachine::Initialize()` only invokes `CASE_LearningMigrator` when `InpAceV4MigrateFromTag != ""` AND both `m_v4Adaptive.HadExistingState()` and `m_v4Analytics.HadExistingState()` are false (i.e. this is the first run of this version for this symbol) — a mid-run restart of the same version never re-imports. Whatever the outcome, a `MIGRATION,<1|0>,<sourceTag>,<reason>,<timestamp>` row is written by each engine's own `SaveState()` the next time it runs (once per process, then cleared), and `LoadState()` skips that row like a comment on read.

## Phase 1 — same-setup comparison vs legacy

**The problem.** V4's own learning stats (`LearningStatsTable`, per-archetype/regime/DNA) and legacy's trade stats have never shared a key. Two piles of numbers, no linkage — so "is V4 actually better than legacy" could never be answered with real paired data on the same setup, only by eyeballing two separate averages that might be describing completely different market conditions. Separately, every legacy trade V4 classified `ARCH_NONE` was silently dropped from all V4 learning (Phase 0's comment on `RecordClosedTrade()`) — the case where V4 had nothing to offer but legacy traded anyway was invisible.

**The four-cell design.** A new `ComparisonLedger` (Models/ASE_AdaptiveTypes.mqh) holds one row per `"<archetype>|<regime>"` key, plus one `"NoClass"` row, linear-scanned like the existing `LearningStatsTable` (deliberately not indexed by `ENUM_MARKET_REGIME` ordinal — that enum has 7 members, not 5, and a fixed 2D array sized off the wrong assumption would silently miss a regime). Every row tracks four cells based on what actually happened to ONE setup occurrence:
- **both** — V4 would-qualify (`conf.qualified`) AND legacy traded it: the only cell with a genuine apples-to-apples R pair (`sumV4R`, `sumLegacyR`, `count`).
- **v4Only** — V4 would-qualify, legacy did not trade it: theoretical R only.
- **legacyOnly** — V4 did not qualify (grade FAIL/C, or `ARCH_NONE` on the `NoClass` row), legacy traded it: realised R only.
- **neither** — count only; nothing happened worth summing.

`EdgeVsLegacy(archetype, regime)` averages `v4R - legacyR` over the `both` cell only; callers must check `PairedCount()` before trusting a non-zero edge, since 0.0 also means "no paired data yet."

**Threading `wouldQualify` through.** Qualification (`grade`, `qualified`) lives on `ConfluenceResult` at evaluation time, not on `PendingTheoretical` (which only carries entry/sl/tp1/direction/regime). `PendingTheoretical` gains a `wouldQualify` field, set from `conf.qualified` at `RegisterPending()` time (called from `RecordOpportunity()`, which already receives the full `conf`). It's threaded through `ResolvePending()`'s parallel `m_resolvedWouldQualify[]`/`m_resolvedRegime[]` arrays and out through `GetNextTheoreticalOutcome()`'s two new out-params, the same pattern already used for `hasLiq`/`oppId`/`legacyTraded`.

**Joining the "both" cell across two async events.** When legacy traded a V4-qualifying setup, its theoretical R resolves at the M15 bar close (`ResolvePending`/`GetNextTheoreticalOutcome` in `ASE_SetupAnalytics.mqh`, drained in `StateMachine::Update()`) and its realised R exists only once the real trade closes (`RecordClosedTrade()`) — two events with no fixed ordering. `CASE_StateMachine` gains a small oppId-keyed join buffer (`m_pendingCompareOppId/Arch/Regime/R/Stamp[ASE_MAX_PENDING_COMPARE]`, 40 slots) and `StashOrResolveCompareBoth()`: whichever side arrives first stashes its R under the shared `oppId` (Phase 0 already guarantees entry snapshots and pending theoreticals share it); whichever arrives second finds the stash, calls `ComparisonLedger::Add()` with both R values, and clears the slot. Deliberately placed on `CASE_StateMachine` rather than `CASE_SetupAnalytics` or a new class, since it needs write access from both the M15 resolution loop and `RecordClosedTrade()`, which already both live there — avoids inventing cross-object plumbing for a 40-row lookup table. An unresolved half is evicted with a one-line `Print()` warning after `ASE_COMPARE_JOIN_TIMEOUT_SECONDS` (200 M15 bars, ~2 days) — deliberately much longer than `InpAceV4TheoreticalMaxBars`, since the real trade for a setup can easily still be open well after its theoretical twin has already resolved.

**The NoClass row.** In `RecordClosedTrade()`, when the entry snapshot's `m_v4EntryConf.archetype == ARCH_NONE` (previously silently skipped for all V4 learning), the realised R now routes to the ledger's `NoClass` row as a `legacyOnly` observation. A classified-but-unqualified legacy trade (archetype present, `grade` FAIL/C) routes `legacyOnly` on that archetype's own row instead, using the real R directly — there is no V4 theoretical side to join against, because `wouldQualify==false` is exactly the condition under which the M15 loop skips the join for that `oppId`. When `m_v4EntryValid` is false (V4 wasn't running at entry), nothing is recorded — "V4 wasn't watching" is not the same claim as "V4 saw nothing." Risk-unknown closes (`riskMoney<=0.0`) are excluded from every comparison path, same as the existing adaptive-engine guard, so a fallback 0.0 R is never recorded as if it were a genuine flat outcome.

**Persistence.** The ledger lives on `CASE_SetupAnalytics` (it already owns `oppId` generation and the pending/resolution machinery that produces `wouldQualify`/`legacyTraded` — keeping the ledger here avoids threading that state out to `CASE_AdaptiveEngine` just to persist it). `SaveState()`/`LoadState()` gain a `COMPARE,<key>,bothCount,sumV4R_both,sumLegacyR_both,v4OnlyCount,sumV4R_v4Only,legacyOnlyCount,sumLegacyR_legacyOnly,neitherCount,firstSeen,lastSeen` row per populated row. `LoadState()` parses it tolerantly — a pre-Phase-1 state file simply never has the tag, the branch never triggers, and the ledger stays at its `Reset()` default, matching the existing `PENDING`/`PENDING2` tolerance pattern. Pending-theoretical rows persist under a new `PENDING3` tag (`PENDING2` fields + `wouldQualify`); old `PENDING`/`PENDING2` rows still load with `wouldQualify` defaulting to false. The in-memory join buffer is NOT persisted — it's a short-lived join for two events expected within `ASE_COMPARE_JOIN_TIMEOUT_SECONDS` of each other, not learning state, and is explicitly cleared in `Initialize()`.

**Reporting.** `CASE_SetupAnalytics::BuildComparisonReport()` formats one line per active row: paired count, `EdgeVsLegacy`, v4-only count, legacy-only count, neither count. `CASE_V4Dashboard`'s 16 on-chart label slots are already all in use (see `Core/ASE_V4Dashboard.mqh`), so there's no clean chart slot for this without reworking that budget — the report instead prints via `Print()` once per M15 bar, alongside Phase 0's periodic save block in `StateMachine::Update()`, gated the same way (`InpAceV4Mode >= ACEV4_EVIDENCE`).
