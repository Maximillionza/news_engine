# Session Handover — 2026-08-14

## What this project is

`news_engine` — scores directional probability (XAUUSD primary, US30 also
configured) ahead of major USD economic releases. Two deliberately
separate pipelines:

1. **Essence-only dashboard** (`webapp/`) — pure calendar math
   (forecast vs. actual, no articles). `webapp/scheduler.py`'s background
   loop is the SOLE live Forex Factory fetcher; `webapp/scoring_service.py`
   computes a probability from forecast/previous/actual alone.
2. **Article-based accumulator** (`scoring/backtest_accumulator.py`) —
   real RSS/Alpha Vantage articles, sentiment scoring, print-direction
   lexicon inference, trend-streak feedback, Kalshi prediction-market
   reads. Runs as its own background process (`scripts/run_accumulator.py`).

Two established, deliberate cross-pipeline reads (both read-only,
fail-open): `webapp/app.py` reads `scoring/backtest_store.py`'s DB for
the print-call badge; `scoring/backtest_accumulator.py` reads
`webapp/store.py`'s DB for the trend signal. Any NEW cross-pipeline read
must follow this exact pattern.

Launcher: `python scripts/run_all.py` starts both processes together,
tagged combined output, Ctrl+C stops both.

search-summary research and even the plan's own drafted code were wrong
multiple times:

  plan now (both legacy `/api/v3/` and current `/stable/` rejected the
  user's real key). Do not trust this session's own earlier research on
  FMP being free — it's wrong now.

  spot-check.

claim comes from search-result synthesis rather than a real API call,
verify live before designing/building around it. This session got burned
enough times that it's now a standing practice, not a one-off.

## IN PROGRESS — exact state when this handover was written

**Task:** the essence-only score's `direction` field (the PRIMARY gauge
on each dashboard card) still shows `"pending"` for CPI m/m, PPI m/m,
Core CPI m/m — even though real actuals now exist in `event_history` via
the actuals-fallback script.

**Root cause, confirmed:**
- `webapp/scoring_service.py`'s `score_event_for_symbol()` computes the
  essence-only score from an `EconomicEvent` object's own `.actual` field.
- The essence-only score is computed and PERSISTED once per
  `webapp/scheduler.py` cycle (`run_scoring_cycle()`), against freshly
  live-fetched `EconomicEvent` objects — NOT recomputed live on each
  `/api/predictions` request. `webapp/app.py`'s `/api/predictions` route
  just reads the STORED `prediction_runs` row (`get_latest_two()`).
- `fill_missing_actuals.py` only wrote to `event_history` (a separate
  table) — it never touched `calendar_snapshot` (the persisted JSON blob
  `get_calendar_snapshot()` returns, sourced from FF's own feed) or
  `prediction_runs` (the persisted essence-only score).
- Confirmed live: `GET /api/calendar` still shows `actual: null` for
  CPI m/m / PPI m/m / Core CPI m/m, while `event_history` (queried
  directly) has real values for the same occurrences.
- Additional wrinkle discovered mid-diagnosis: because the FF rate-limit
  guard (shipped just before this) now blocks most fetch attempts,
  `run_scoring_cycle()` frequently short-circuits at the `fetch_calendar()`
  call itself (caught by the existing broad `except Exception`, logged as
  "calendar fetch failed, keeping existing data") — so simply "merging
  event_history's actual into the next live fetch" won't fire again for
  a while, and isn't a fix a user can observe soon.

**Decision already made with the user:** "read-time merge" approach —
when event_history has a real actual but the calendar snapshot / a
stored prediction_runs row is still stuck showing pending, treat
event_history as authoritative and reflect that at READ time (not by
duplicating writes into calendar_snapshot from every fallback script).
User explicitly chose this over "write-time duplication" (having every
fallback script also update calendar_snapshot directly — rejected as
two places to keep in sync, won't generalize to future fallback paths).

**Not yet decided/implemented:** the exact mechanics of the read-time
merge, because of the wrinkle above — a pure "merge at
`get_calendar_snapshot()`'s read" only fixes the calendar snapshot's own
displayed forecast/actual text and `/api/calendar`'s output; it does
NOT by itself cause `/api/predictions`'s `direction` field to stop
saying "pending", because that field comes from the separately-persisted
`prediction_runs` table, written by a PAST scheduler cycle that also saw
`actual=None` at the time.

**Most likely real fix (not yet built, not yet confirmed with the
user):** in `webapp/app.py`'s `/api/predictions` route, when a
`prediction_runs` row is stuck `direction="pending"` AND `event_history`
now shows a real, resolved `actual` for that exact occurrence, recompute
the essence-only score ON THE FLY for that response (calling
`webapp.scoring_service.score_event_for_symbol()` with an `EconomicEvent`
enriched from `event_history`'s real actual) rather than trusting the
stale persisted row — without necessarily writing a new `prediction_runs`
row (that's the scheduler's job/pattern; whether to also persist this
on-the-fly recomputation is an open question worth asking the user).

**Next action for whoever picks this up:** re-confirm this proposed
mechanism with the user (it's a real architectural addition — routes
computing scores on the fly is a new pattern for this codebase, which
has so far kept "routes only read stored data" as an invariant) before
implementing. Read `webapp/app.py`'s current `get_predictions()` in full
first (it's been modified by three separate plans this session — Tasks
7/9 of the UI-redesign plan, plus the two final-review fixes — verify
current line numbers, don't trust anything above).

## Established conventions this session enforced repeatedly

- **"Real data or absent, never fabricated/reconstructed/guessed."**
  Applied to: historical backfill facts, actuals-fallback, Kalshi reads,
  Kalshi liquidity gating, trend-signal minimum-row floors. When in
  doubt, write nothing rather than approximate.
- **Verify live before trusting research/search summaries.** This
  session's single most expensive repeated lesson (Kalshi, FMP, two
  separate backfill data corrections).
- **Two-pipeline separation is deliberate** — essence-only dashboard vs.
  article-based accumulator. Any new cross-pipeline read must be
  read-only and fail-open, same pattern as the two existing exceptions.
- **Subagent-driven-development is the standing execution preference**
  (saved to user memory) — after writing a plan, execute via
  `superpowers:subagent-driven-development` without re-asking which mode.
- **Committed directly to master all session**, no worktrees — established
  by repeated, un-objected-to precedent, not a one-time exception.
- **Restart discipline matters** — every `run_all.py` restart costs real
  external API budget (FF rate limit, Alpha Vantage 25/day). Batch
  verification, don't restart reflexively.
- **Provenance is always marked, never silently blended** — `source`
  columns (`'live'`/`'seeded'`/`'live_web_fallback'`) exist specifically
  so a reader can always tell where a number came from.
