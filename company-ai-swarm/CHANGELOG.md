## [Unreleased]

### Added

- Repository directory structure scaffolded per `Specifications/2 - construction-framework/The Company Repository Blueprint Specification (CRBS).md`.
- Configuration and component templates (no functional code) for agents, departments, workflows, memory, knowledge, and governance objects.
- `IMPLEMENTATION_PLAN.md`: milestone-based, independently-testable phase plan (Phases 0-11).
- **Phase 0 (Foundation & Contracts)**: Python/FastAPI/SQLAlchemy dev environment (`pyproject.toml`, `.venv`), `docker-compose.yml` (Postgres), RCS message contracts as validated Pydantic schemas (`services/shared/contracts.py`), API Gateway health-check endpoint, `Documentation/operations/technology_decisions.md`. 14 tests passing.
- **Phase 1 (Identity & Security Core)**: `identity_service` (create/read identity records, ESTAS sec.5-7), `security_service` (permission evaluation + audit log sink, ESTAS sec.9/sec.24). MVS Test Category 007 (Security Validation) passes: no-identity, insufficient-permission, and correct-permission cases, each denied/allowed and logged as specified. 5 tests passing.
- **Phase 2 (Data Layer & Memory Substrate)**: `memory_service` implementing the canonical EMAS five-tier hierarchy (Working/Project/Department/Enterprise/Historical), every access routed through Phase 1's `security_service.authorize()` per ESTAS sec.16; `knowledge_service` (entity/relationship storage, EKGS Object Model, not yet wired to a graph engine); `shared/vector_store.py` and `shared/object_storage.py` substrates. Fixed a "domain" field naming collision inherited from the source memory_object_template.yaml (tier vs. subject-domain), consistent with the drift-correction discipline applied during the Specifications/ reconciliation. Exit criteria met: write/read at all five tiers with all EMAS-required fields persisted, and Project-tier and Department-tier queries demonstrate no cross-scope leakage. 23 new tests passing (42 total).
- **Phase 3 (Runtime & Communication Backbone)**: `shared/service_bus.py` (`InMemoryServiceBus` - RCS request/response dispatch), `event_service` (`InMemoryEventBus` - async pub/sub), `observability_service` (`TelemetrySink` per RCS sec.18 / EOCCS sec.6). Both buses authorize every operation through `security_service.authorize()` using the message's own `security_context` before delivery, and both emit telemetry regardless of outcome. Added `security_context` to `EventContract`, which was missing it since Phase 0 - a genuine gap, not a stylistic fix, since RCS Principle 002 requires it on every action. Found and fixed a real bug during testing: both buses used `telemetry or default_sink`, and since `TelemetrySink` defines `__len__`, a freshly-created *empty* sink evaluated as falsy and was silently replaced by the wrong sink - changed to explicit `is None` checks. Exit criteria met: synthetic service registration + request/response, and publish/subscribe, both succeed, both produce telemetry with component/action/timestamp/duration fields, and both enforce security_context. 9 new tests passing (51 total).
- **Phase 4 (Agent Runtime, single agent, no orchestration)**: `agent_runtime` (new service directory, not in CRBS's explicit list - same kind of addition as `services/shared/`): `registry.py` parses the already-scaffolded `agents/active/*/agent.yaml` files into structured `AgentDefinition`s (ADLS sec.4 Core Agent Schema); `runtime.py`'s `AgentRuntime` implements ROM sec.11's ten-step Agent Execution Cycle end to end (Receive Task -> Load Context -> Retrieve Relevant Knowledge -> Check Policies -> Plan Approach -> Execute -> Validate -> Produce Artifact -> Report Outcome -> Release Context), reusing Phase 1's `authorize()`/audit, Phase 2's `query_memory()`, and Phase 3's telemetry throughout. `shared/model_gateway.py` (`ModelGateway` + `StubModelProvider`) is the only object in the codebase permitted to hold a model reference - `AgentRuntime` cannot reach a model except through it, verified by a structural test, not just a behavioural one. Exit criteria met: `research_agent_001` executes a real (canned) task against the real scaffolded `agent.yaml`, with no COO involved; all ten cycle steps appear in telemetry; an audit record documents completion; the model gateway's call count is exactly one. 7 new tests passing (58 total).
- **Phase 5 (COO + Research Department, MVP Build Order Version 0.1)**: `orchestrator` implements COOS's full Operating Cycle (sec.6) wired to Research only - `planner.py` (Objective Understanding + Task Classification + Department Selection, sec.7-9/sec.12), `allocator.py` (Agent Allocation, sec.13, Capability Match only), `router.py` (dispatches to Phase 4's `AgentRuntime`), `evaluator.py` (Outcome Validation, sec.20), `controller.py` (`COOOrchestrator`, sec.6), `decisions.py`/`models.py` (COO Decision Record persistence, sec.22). Fixed two real data inconsistencies found while wiring department-to-agent routing, not just naming polish: `departments/*/definition.yaml` capability lists used entirely different vocabulary than their agent's actual `agent.yaml` capabilities (e.g. "market_research" vs "research"), and department `agents:` lists referenced folder names instead of the identity IDs `AgentRegistry` actually keys by - both fixed across all four MVP departments. Found and fixed a real routing bug during testing: the keyword-overlap department matcher (a genuine algorithm, not a stub - see `Documentation/operations/technology_decisions.md`) ranked the empty, out-of-scope "Strategy Department" above Research on the test objective, because its mission text happened to share more vocabulary; fixed by excluding departments with no assigned agents from consideration, since such a department is never a viable dispatch target regardless of text similarity. Removed CRBS's originally-scaffolded empty `planner/`/`allocator/`/`router/`/`evaluator/`/`controller/` subdirectories in favour of flat modules, matching every other service's structure. Exit criteria met: "Create a market intelligence report" routes to Research, executes via `research_agent_001`, produces output, and a Decision Record captures reasoning/chosen action/outcome - reproducibly across repeated runs. 5 new tests passing (63 total).
- **Design decision (pre-Phase 8/9, no code yet)**: reviewed a separate swarm project ("Idea Lab") for repurposable patterns; user adopted two, by explicit instruction, into `IMPLEMENTATION_PLAN.md` and `Documentation/operations/technology_decisions.md` ahead of the phases that will build them. (1) Phase 8 gains a four-condition escalation policy as ESTAS sec.10's Risk Assessment step, substituting for COOS sec.9's undefined numeric risk score. (2) Phase 9's previously-unspecified "Learn" step (COOS sec.6 memory promotion) is now defined as tiered: minor lessons self-approved by the COO onto the Historical tier, critical lessons (any workflow that tripped a Phase 8 escalation condition) held for async human approval while the COO continues Business-As-Usual on other objectives - with an explicit, non-optional fallback to human-approval-only for everything if the split proves to add complexity, errors, or bias. Everything else reviewed from Idea Lab (deterministic routing table, Vendor/Panel distinction, standalone deferred-log artifact) was explicitly declined.
- **Phase 6 (Multi-Department Expansion, MVP Build Order Version 0.2)**: `services/workflow_engine/` (`models.py` - `TaskRun`/`WorkflowRun`, EWOS sec.5/sec.11 fields Phase 6 actually populates; `engine.py` - `execute_workflow()`, department-level Task Decomposition (EWOS sec.10) + Sequential Execution (EWOS sec.14) only, halting on the first failed task, no Parallel Execution (sec.13) yet). `orchestrator/planner.py` gained `select_all_matching_departments()`, extending Phase 5's keyword-overlap matcher to multi-department objectives, ordered by a fixed canonical department sequence rather than a real dependency graph (no such mechanism exists in the corpus - see `technology_decisions.md`). `orchestrator/controller.py`'s `receive_objective()` now branches: exactly one matched department keeps the unchanged Phase 5 path (`ObjectiveOutcome`); more than one delegates to `workflow_engine.execute_workflow()` (`WorkflowObjectiveOutcome`) - Phase 5's tests were re-run unmodified and still pass, confirming this was additive, not a rewrite. Found and documented, not fixed, during this phase: all four MVP departments' `definition.yaml` files already carry a capability-aligned agent since Phase 5, not just Research's - so the multi-department matcher can already reach Compliance/Operations ahead of their documented Phase 7/8 activation; this is existing, correct department data, not a gap, and no phase-lock was added to restrict it. Exit criteria met: "Research market analysis and build working software" decomposes into a Research -> Engineering workflow, both agents execute in that order via the unmodified Phase 4 `AgentRuntime`/Phase 5 `router.dispatch()`, and a Decision Record captures both agents and the combined outcome. 5 new tests passing (68 total).
- **Phase 7 (Knowledge Graph + Full Roster, MVP Build Order Version 0.3)**: `services/workflow_engine/review.py` implements TDL sec.17's risk-proportional Task Review tier table (`determine_review_tier`); `services/workflow_engine/knowledge.py` records `Agent --USES--> Capability --APPLIES_TO--> Workflow` (EKGS sec.5, UOL sec.6) to `knowledge_service` for every completed task. `workflow_engine/engine.py`'s `execute_workflow()` now special-cases "operations" (the Review Agent's department, activated this phase to complete the MVS-canonical four-department roster): rather than running it as a substantive task on the original objective - which would contradict `review_agent/agent.yaml`'s own stated mission ("Does not perform the original work it reviews") - it dispatches a review task once every other matched department succeeds, and records that task to the Knowledge Graph too. `knowledge_service/repository.py` gained `get_or_create_entity` (Phase 2's `create_entity` fails on the duplicate-PK case this phase now hits routinely, by design - see `technology_decisions.md`). Fixed while wiring this, not a new gap: `orchestrator/planner.py`'s fixed complexity label was `"Level 2 Moderate"`, which doesn't match TDL sec.7's actual tier name (`"Standard"`) - harmless until Phase 7 needed exact string matching against TDL's vocabulary; corrected to `"Level 2 Standard"`. Exit criteria met: "Research requirements, assess risk, and build software while monitoring quality." decomposes into Research -> Engineering -> Compliance -> Review, the Review Agent produces a pass/fail validation with documented reasoning (tier: `peer_review`, the only tier this phase's fixed-default complexity can produce), and the `Agent USES Capability APPLIES_TO Workflow` relationship path resolves via `knowledge_service.get_relationships_for_entity()`, including across repeated runs against the same Agent/Capability entities. 8 new tests passing (76 total).
- **Phase 8 (Governance Completion, MVP Build Order Version 0.4)**: four deliverables.
  (1) **Four-condition escalation policy** (`orchestrator/escalation.py`/`escalations.py`, new `EscalationRecord` in `orchestrator/models.py`) wired into both `controller.py` dispatch paths: NO_MATCHING_DEPARTMENT, OUTCOME_NOT_ACHIEVED, GATE_INTEGRITY_SUPERFICIAL (new `workflow_engine/gate_integrity.py`, TDL sec.13/14), UNRESOLVABLE_DEPENDENCY_GAP (`workflow_engine/engine.py` now halts gracefully with `blocked_reason` instead of raising on a missing agent), plus TECHNICAL_FAILURE for any unhandled exception, caught, logged, and re-raised - never conflated with the four framework verdicts. Two of the four conditions (OUTCOME_NOT_ACHIEVED, UNRESOLVABLE_DEPENDENCY_GAP) turned out unreachable through `receive_objective()`'s real dispatch path with this codebase's stub provider and real department files - documented in `technology_decisions.md` and tested as direct exercises of the same functions instead of contrived end-to-end scenarios.
  (2) **Compliance Intelligence Engine** (`compliance_service/applicability.py` - ECRIS sec.8's six-factor Applicability Assessment via a small seeded rule registry, POPIA taken from ECRIS's own worked example, unrecognized regulations return UNKNOWN rather than a silent `False`; `policy_impact.py` - MVS-008's Policy Added -> Impact Analysis -> Workflow Review -> Control Recommendation flow, reusing `planner.py`'s keyword matcher).
  (3) **Observability Platform** (`observability_service/views.py` - Director/COO/Department views, EOCCS sec.22-24, over existing telemetry + Decision/Escalation Records; `alerting.py` - EOCCS sec.25's Information/Warning/High Risk/Critical ladder, rule-based over DENIED/FAILURE telemetry and unresolved escalations).
  (4) **Security monitoring completion** (`security_service/trust.py` - ESTAS sec.26 Trust Scoring from audit-trail error rate only, persisted onto `Identity.trust_level`, not yet wired into permission enforcement; `incidents.py` - ESTAS sec.28's seven-stage Incident Workflow as a forward-only state machine, intentionally not wired into the escalation policy - distinct concerns per ESTAS's own Trust/Authority/Autonomy separation).
  Found and fixed while writing this phase's Gate Integrity Check test, not designed for it up front: a lone department match on "operations" previously took the single-agent dispatch shortcut, sending the raw objective straight to the Review Agent - contradicting its own mission. Fixed in `controller.py` to route any "operations" match through `workflow_engine`, same as any other multi-department case; this also happens to be exactly the scenario Gate Integrity Check condition 3 needs (a review with nothing to review). Exit criteria met: MVS-008 and MVS-009 pass as formal tests (requirement/impact/evidence for compliance; logs/metrics/traces/performance data for a real four-department workflow run), and all four escalation conditions plus the technical-failure path are independently reproducible and correctly classified. 29 new tests passing (105 total).
- **Phase 9 (MVP Validation, Version 1.0)**: three deliverables plus the full MVS acceptance suite.
  (1) **Tiered Learn step** (`orchestrator/controller.py._learn()`, new `memory_service/promotion.py`): COOS sec.6's previously-unimplemented Learn step, reusing Phase 8's Escalation Records as the sole criticality signal per the user's earlier design decision - zero escalations for a decision means "minor" (self-approved straight to Historical tier); any escalation means "critical" (held at Project tier as a `LessonPromotion`, pending human `approve_promotion()`/`reject_promotion()`, which always writes a brand-new Historical-tier memory object rather than mutating the pending one). Both this and (2) below are best-effort: a missing `memory:<tier> write` grant is caught, audited, and never allowed to undo an already-completed objective - see `technology_decisions.md` for why most earlier phases' fixtures don't need updating.
  (2) **Department-observation memory write** (`orchestrator/router.py`, inside `dispatch()`): every successfully-completed task now records a Department-tier OBSERVATION memory object - the missing half of a mechanism `agent_runtime/runtime.py` has had since Phase 4 (Retrieve Relevant Knowledge already queried Department-tier memory; nothing had ever written to it). This is what makes MVS-005's "second execution improves via stored knowledge" literally true rather than aspirational - defined honestly as growth in retrievable memory, not a fabricated quality delta, since no real model or scoring mechanism exists anywhere in this corpus.
  (3) **Model Gateway hot-swap** (`shared/model_gateway.py`'s `ModelGateway.replace_provider()`), for MVS-010 Failure Recovery - a manually-triggered provider swap, not an automated detect-and-recover daemon.
  Found and fixed while writing the acceptance suite's own fixtures, not a pre-existing bug: a test helper's `telemetry or TelemetrySink()` silently discarded a freshly-passed-in empty sink - the exact `__len__`-makes-empty-falsy bug already fixed in Phase 3's `service_bus.py`/`event_service`, reintroduced here and caught immediately by a failing assertion, not shipped.
  Exit criteria met: `Tests/acceptance/test_mvs_acceptance.py` formally re-confirms all ten MVS-numbered pass criteria at this phase boundary (with 002 Agent Lifecycle, 005 Memory Validation, and 010 Failure Recovery newly and thoroughly covered, since their mechanisms didn't exist before this phase); Test Category 011 (Evolution) remains explicitly out of scope, deferred to Phase 11. 20 new tests passing (125 total). Per MVS sec.19, The Company is operational: it can receive objectives, organise itself, execute work, remember outcomes, improve safely, and operate under governance.
- **Phase 10 (Expansion Layer, post-MVP)**: four deliverables.
  (1) **SDK** (`sdk/`, now on `pythonpath`): `sdk/validation/pipeline.py` implements ESDKS sec.7's generic five-gate `ValidationReport` shape; `sdk/agent_builder/builder.py`'s `build_agent()` is the only component that exercises all five gates (Schema Validation -> Security Review -> a real Capability Test through the unmodified Phase 4 `AgentRuntime` -> Architecture Check -> Activate, writing `agent.yaml` and registering into a live `AgentRegistry`) - this is also the piece Phase 10's own exit test requires. `sdk/capability_builder/` and `sdk/workflow_builder/` produce validated `Capability`/`WorkflowTemplate` objects (Schema Validation only) but are explicitly not yet wired into department/agent capability matching or `workflow_engine.execute_workflow()` - named gaps, not silently dropped (see `technology_decisions.md`). Department Builder (ESDKS sec.5.2) was skipped - it isn't in ESDKS sec.16's own MVP SDK Requirements list. "Tool interface" was folded into the Plugin service's Tool Plugin type rather than a second, parallel tool schema.
  (2) **Plugin Registry** (`services/plugin_service/`, data lives under `plugins/registry/` per CRBS's data-dir/service-code split): full EPAS sec.6 lifecycle (register -> validate -> approve -> activate/disable) and sec.10 Agent Plugin Access (`grant_agent_access()`, logged via the existing `security_service` audit trail). Capability Test and Integration Test (EPAS sec.8) are named, not implemented - no plugin runtime exists anywhere in this corpus to test against.
  (3) **Marketplace Registry** (`services/marketplace_service/`): full EMAS sec.7 lifecycle (submit -> validate -> publish -> retire) across the four asset types, search by name/capability/type, and evaluation tracking as a running average (not EMAS sec.13's undefined Capability Ranking formula). Technical and Performance Validation (EMAS sec.9) are named, not implemented, same reasoning as the Plugin Registry.
  (4) **API Gateway** (`apps/api_gateway/main.py`): `POST /objectives`, `GET /objectives/{decision_id}`, `GET /agents` wired to the unmodified `COOOrchestrator` - no new orchestration logic. A single static `X-API-Key` header is an explicit placeholder for real authentication. Dev-mode now persists to a SQLite file (gitignored) instead of in-memory, since in-memory SQLite is scoped per-connection and would lose bootstrapped identities/permissions between requests.
  Exit criteria met: a new agent ("Data Science Agent," not one of the original four) is defined via the SDK alone, registers in the Agent Registry, and executes successfully through `orchestrator/router.py`'s unmodified `dispatch()` - the shared dispatch path every task in this codebase has gone through since Phase 5 - without editing any core runtime file. 29 new tests passing (154 total).
- **Phase 11 (Intelligence Systems, post-MVP, final phase)**: three deliverables, closing MVS Test Category 011.
  (1) **Digital Twin** (`services/digital_twin_service/`): `capture_snapshot()` pulls real current state from the `AgentRegistry`, `DepartmentRegistry`, and recent COO Decision Records into a persisted `DigitalTwinSnapshot` - synchronised on demand, not via a continuous event feed (no durable change log exists anywhere in this corpus).
  (2) **Simulation Framework** (`services/simulation_service/`): only the Workflow Simulation Engine (ESDTS sec.11/12.5) is built. `simulate_workflow_change()` runs a real dry run - both a baseline and a proposed department list executed through the unmodified `workflow_engine.execute_workflow()`, each in its own throwaway in-memory database and freshly-granted identities, never the caller's real session, so a simulation cannot write production state (ESDTS sec.9's Environment Separation, taken literally rather than policy-enforced). `SimulationRun` implements ESDTS sec.14's canonical `simulation_input`/`simulation_output` schema - the spec's own text names this the schema that supersedes two other drifted variants elsewhere in the corpus. `confidence` is fixed low (0.4) with the reason spelled out in `limitations`, since no real model or business-outcome measure exists anywhere in this codebase.
  (3) **Evolution Engine** (`services/evolution_service/`): `detect_inefficiencies()` reuses Phase 8's GATE_INTEGRITY_SUPERFICIAL escalation condition (a review that ran with nothing to review) as the one real, already-produced inefficiency signal in this codebase - not a synthetic inefficiency invented for this phase's test. `EvolutionEngine.detect_and_propose()` (EESIS sec.11: Analyse -> Request simulation -> Propose) always creates a PENDING `ChangeProposal`; `approve_change()`/`reject_change()` require an identity that passes `security_service.authorize()` against `evolution:change_proposal` - the engine's own identity is never granted this by anything in this codebase, so "the Evolution Engine cannot self-approve changes" (EESIS sec.10, ESTAS sec.21) is enforced structurally, by the absence of a grant, not a special-cased check. `implement_change()` raises unless the proposal is already APPROVED, and writes an EESIS sec.14 Evolution Memory record via `memory_service.write_memory()` at the Historical tier - reusing Phase 9's Learn-step infrastructure. Deliberately does not automatically mutate `workflow_engine`'s runtime behaviour for future objectives - named, separate follow-up work, not claimed here; mirrors Phase 9's own precedent that an approved lesson promotion writes memory without automatically changing agent behaviour either.
  Exit criteria met: the full loop (Observation -> Evolution Engine -> Simulation -> Recommendation -> Approval -> Implementation) completes for a real inefficiency (an "operations only" objective's superficial review, the same real signal exercised since Phase 8), with the engine's own two attempts to approve/implement without human sign-off both raising, and a human-approved implementation producing a Historical-tier Evolution Memory record. 8 new tests passing (162 total).
